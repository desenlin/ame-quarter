# GitHub storage and hosting audit

Audit date: September 24, 2026 (America/Los_Angeles).

**Conclusion:** the current district and the CRE studio prototype fit comfortably within normal GitHub repository and GitHub Pages limits. No Git LFS, external model store or paid server is needed at this stage. The important constraint is the viewer’s graphics performance, not the number of objects stored on GitHub.

## Measured files

- Original standalone district: **760,487 bytes**, approximately **0.76 MB**.
- Complete portable studio, including its embedded 3-D renderer and district: approximately **0.83 MB**.
- Largest individual source file: the bundled Three.js renderer, approximately **0.60 MB**.
- The modular website starts with just the interface, lease data and financial code; the renderer and scene are requested when the user chooses **Explore 3-D**. See `size-audit.json` for the exact initial transfer and full-visit payload estimates.
- The source tree is roughly **1 MB**, before Git history and excluding development dependencies. There are no large GLB models, videos or photographic texture files; buildings, goods, plants and most textures are generated by code.

Units here are decimal MB (1,000,000 bytes). GitHub’s single-file limits below use MiB (1,048,576 bytes). Gzip figures in the JSON audit are local compression estimates, not a measurement of GitHub’s HTTP transfer.

## GitHub’s published limits

| Constraint | Published limit | Implication |
| --- | --- | --- |
| Regular Git file | Warning above 50 MiB; blocked above 100 MiB | All current files are far below both thresholds |
| Browser file upload | 25 MiB per file | Current files fit |
| Pages published site | Maximum 1 GB | Current project is roughly three orders of magnitude smaller |
| Pages source repository | Recommended maximum 1 GB | Avoid committing exports and generated archives repeatedly |
| Pages bandwidth | Soft limit of 100 GB/month | Classroom-scale use has substantial headroom at the present payload |
| Pages deployment | 10-minute timeout | A static site needs no application server or heavy build |
| Pages builds | Soft limit of 10/hour; custom Actions workflow exception | Ordinary prototype updates are well within the intended use |

Official sources, checked for this audit:

- [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

A rough transfer budget is visits × downloaded bytes. At about 0.83 MB for a full portable load, 1,000 uncached loads are about 0.83 GB before HTTP compression, caching and optional font requests. This is an estimate, not a traffic guarantee. A separate project repository improves organization but does not make resource usage unlimited.

## Rendering versus hosting usage

Rendering runs in each visitor’s browser on their own device. Orbiting, walking, weather changes and animation do not consume GitHub GPU time or GitHub Actions minutes and do not stream a new image from the server each frame. New or uncached page loads do consume hosting bandwidth; heavy traffic can approach GitHub Pages’ soft bandwidth limit. Opening 3-D in a separate tab uses the same scene assets and the browser may reuse its cached files.

## Browser constraints

The constructed scene contains **1,306 mesh nodes**, **16,139 instanced copies**, **322 static material/geometry batches**, **624 materials** and **166 textures**. These counts are not frame-by-frame draw calls: visibility, material groups, shadow passes and reflections affect actual work.

Measured unique geometry attributes and indices occupy about **2.44 MB**; instance matrices add about **1.03 MB**. Generated texture storage is approximately **35.5 MB** under an RGBA8-plus-mipmaps estimate. These are partial resource estimates, not peak process or GPU memory. Shadow maps, reflection targets, framebuffers, CPU copies, object overhead and the driver add more. See the raw `scene-audit-*.json` files.

Full graphics uses a directional shadow, six storefront shadow lights, two planar reflection layers, and a cached six-face environment capture. The scene also evaluates 21 spot lights and six point lights. This is substantially more expensive than serving its compact source files. Frame rate cannot be inferred from HTML size.

## Mitigations in this prototype

1. Start on a native HTML leasing plan. Financial controls do not depend on WebGL.
2. Load the modular 3-D scene only when requested. The portable single-file review copy contains all code but delays scene construction until requested.
3. Use **Balanced** graphics by default: pixel ratio capped at 1, one 1024-pixel directional shadow map, no planar-reflection rendering, and no storefront shadow passes. Geometry, lighting, weather modes and environment highlights remain.
4. Keep **Full reflections** available: the original visual treatment, pixel ratio capped at 1.6, 2048-pixel directional shadow, storefront shadows and both reflection planes.
5. Suspend simulation/rendering when another studio panel or the leasing plan is open, when the scene is offscreen, or when the browser document is hidden. **Close 3-D** removes the iframe.
6. Preserve existing instancing and shared material/geometry batching.

## Growth and launch recommendation

- Keep source, vendor licenses and static entry files in the repository. Keep `node_modules`, QA captures, large exports and release ZIPs out of Git history.
- If photographic textures or imported models are introduced, set per-asset budgets and consider texture compression, mesh simplification and levels of detail before changing hosting.
- Test actual frame rate, load time and memory on a typical student laptop and phone before public launch. No browser FPS or peak-memory benchmark was available in this session; DOM and scene-structure tests are not substitutes for device testing.
- GitHub Pages is appropriate for this static educational prototype. If the studio later becomes a commercial SaaS or facilitates commercial transactions, reassess hosting: GitHub Pages expressly restricts those uses. Accounts, shared saved scenarios and database writes would also require services beyond a static page.

GitHub Pages was enabled after explicit publication approval on September 24, 2026 (America/Los_Angeles), using the `main` branch and repository root. The published studio is at `https://desenlin.com/ame-quarter/`. The initial Pages deployment succeeded; live interface interactions and the separate-tab scene link were checked. The cloud browser lacks WebGL, so actual 3-D performance still requires a device with hardware acceleration.
